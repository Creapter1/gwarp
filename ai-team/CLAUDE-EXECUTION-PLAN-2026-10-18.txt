HARD GATES
- Before integration/runtime evidence, confirm the active Claude interface label is exactly “Claude Opus 5.5”. If not exact or unclear, do read-only work only and notify owner.
- Owner approval is required before live integration, release, deployment, or irreversible actions.
- Establish the current baseline commit and relevant file hashes before editing. Ask if the known-good baseline or canonical deployed URL is unclear.
- Never rewrite app.html wholesale. Small, localized changes only. Keep app.html/index.html untouched unless the owner explicitly authorizes the specific change.
- Work in the authorized branch/copy. Never silently overwrite another AI's files or edit another AI's folder.
- Never claim tests, screenshots, integration, rollback, or deployment that did not actually happen.
- Do not bypass permission prompts or disable safety controls just to run longer.

THE TOKEN RULE
Read narrowly. Search for the exact symbol/selector, then inspect only its surrounding implementation and direct dependencies. Do not dump large files or repeat research already answered by a current report. No speculative essays, no repeated plan restatements, no more than one fix candidate per issue unless evidence says it failed. Run cheap checks first, then targeted tests. Report only decisions, evidence, risks, and next action.

WORK LOOP (repeat until the allowed work window ends)
1. CLAIM one bounded task from CONTINUOUS-WORK-QUEUE or the ordered priorities below.
2. Define in 2–4 lines: observed problem, exact target, measurable acceptance test.
3. Inspect the current source and relevant candidate/report only. Mark unknowns UNSURE.
4. Reproduce the issue if possible. If not reproducible, record what was attempted; do not invent a cause.
5. Make one minimal change in the authorized working copy only if the evidence supports it. Otherwise create a concise finding/blocker and move to the next independent task.
6. Run syntax/static checks, then the smallest meaningful runtime test. Run broad regression only for shared runtime, serialization, or cross-cutting UI changes.
7. Save a checkpoint: changed files, base commit, tests and actual results, remaining risks, rollback, exact next step.
8. Update the task/queue status truthfully. Continue with the next eligible task; do not stop after writing a report if other ready tasks remain.
9. Before context fills or the session ends, write the checkpoint to a file so a fresh context/session can resume without rereading old chat.

TWO-HOUR WORK SCHEDULE (flexible; do not pad time)
- First 10 minutes: verify gates, baseline, queue, and current state. Do not repeat completed audits.
- Next 45 minutes: highest priority — reproduce and measure the reported freeze/slow Stop issue in a safe test copy; inspect actual clone limit and Stop path; test the existing clone-safety candidate. Report measured baseline and outcome.
- Next 30 minutes: fix/test one proven root cause, or if not reproducible, create the smallest useful diagnostic/test harness and record blockers. Do not bundle unrelated limits or UI changes.
- Next 20 minutes: run focused regression tests and review one ready candidate from the queue, preferably collision behavior or a high-risk Scratch semantic case.
- Next 10 minutes: correct candidate statuses, record evidence and rollback details, update checkpoint/log.
- Remaining time: continue the queue with the next unblocked, owner-approved task. Good options: costume tool isolated harness, .pmp fixture validation, Scratch-link consent/load tests, Gemini extension permissions/navigation tests, Buffy-labelled add-on lifecycle tests.
This schedule is a guide, not a timer. If a stage is blocked, record why and continue only with an independent task that is allowed. Never invent work to fill two hours.

CONTEXT / TOKEN MANAGEMENT
If using Claude Code:
- Start a new task with /clear when the next task can be understood independently; project files and CLAUDE.md remain available. Preserve the checkpoint first.
- Use /compact when continuing the same task and useful context must survive. Do not repeatedly summarize the whole repo.
- Use /context or the available usage indicator if context is growing; keep source excerpts and tool output targeted.
- Read CLAUDE.md if present. Keep it short and stable; do not repeatedly rewrite it.
- For a multi-file change, first state the intended files and acceptance checks, then execute only after the scope is clear.
- Do not assume commands like /clear, /compact, model switching, or automatic compaction exist in every Claude interface. Use only what the active interface supports.
- Avoid excessive subagents or parallel duplicate audits; use them only for genuinely independent bounded work. The official integration/evidence role stays with the verified Claude session.
- If using Claude chat rather than Claude Code, use the saved checkpoint and start a fresh chat only when needed; don't assume terminal commands are available.
- Keep final updates short (roughly 5–10 bullets) and link detailed evidence rather than pasting it into every handoff.

EVIDENCE LABELS
- SOURCE-VERIFIED: exact current source/Git object inspected.
- STATIC-ANALYSIS: reasoned from source, not executed.
- REPORTED TEST: another contributor's claim, with report linked.
- BROWSER-VERIFIED: Claude actually ran named steps in a named browser/version and recorded results.
- NOT TESTED: no execution evidence.
A file existing, syntax passing, or MERGE-QUEUE saying PICK does not mean fixed, integrated, or browser-tested.
