1. DEEPSEEK COSTUME CANDIDATES — still BLOCKED / HIGH RISK
=====================================================================
Reviewed: LAB-costumes.txt, costume-select-C.js, costume-fill-C.js
(and LAB's stated winners: select-C, fill-C, text-B, eraser-C, undo-C).

What is good
- Honest UNSURE list in LAB-costumes (canvas id, data-gw-shape, GW8.undo,
  mapFor signature, mode field name).
- Safe-ish module shape: early return if GW_V15_COSTUME_EDITOR missing;
  tries GW_DIALOG; feature-off on fill-C.
- Round-2 attack notes (pointer capture, history spam, PNG path) show
  useful lab thinking.

Blocking issues (must fix before any controlled test branch)
1. Wrong state field names vs ENGINE-MAP
   - Code uses CE.state.mode and CE.state.fillColor / fill.
   - ENGINE-MAP documents costumeMode, svgTool, bitmapTool, selectedSvg,
     selectionRect — not mode / fillColor.
   - Severity: HIGH. Modules may always take the wrong branch or wrong color.

2. Assumed DOM attributes with no source proof
   - [data-gw-shape] and [data-gw-selected] are required for select/fill.
   - No confirmation in ENGINE-MAP that production SVG carries these.
   - Severity: HIGH. Select/fill become no-ops or never bind shapes.

3. Parsed SVG not proven to write back
   - select-C mutates a DOMParser document and sets transform/data attrs.
   - Review did not find a call that serializes that DOM back into
     costume.svg / CE.save / VE.save.
   - Severity: HIGH. User sees no persistent change, or editor state diverges.

4. Generic canvas targeting
   - querySelector('#gw-costume-canvas, .gw-paint-canvas, canvas') and
     similar bitmap lists can hit stage or unrelated canvas.
   - fill-C uses document-level click listener (not editor-scoped).
   - Severity: HIGH. Stage/UI clicks can be intercepted.

5. Undo assumptions
   - LAB notes pushHistory('__undo__') is UNSURE; C probes GW8.undo first.
   - Still not SOURCE-VERIFIED that either path performs real undo/redo.
   - Severity: MEDIUM-HIGH.

Minimum correction (DeepSeek's job in deepseek/ only)
A. Source-evidence table: for each API/selector/attribute used, cite the
   exact app.html / ENGINE-MAP line or mark UNSURE and stop using it.
B. Switch CE.state.mode → CE.state.costumeMode; remove fillColor unless proven.
C. Isolate handlers to the confirmed costume canvas only; no bare 'canvas'.
D. Prove write-back path: after SVG edit, call the real save/load API and
   refresh list.
E. Build an opt-in harness that cannot attach until a test flag is set.

Acceptance tests (for Claude later; Grok did not run)
- Vector select/move one shape; costume persists after tab switch.
- Fill SVG + PNG; undo restores both.
- Clicks on stage / block palette never trigger fill/select.
- Feature-off keys disable tools without throwing.

Verdict: Do NOT treat MERGE-QUEUE "PICK" as safe-to-merge. Agree with
ChatGPT 2026-10-15 cross-review: blocked until API map + isolated harness.

3. CHATGPT CLONE-SAFETY — useful candidate, not proven
=====================================================================
Reviewed: chatgpt/clone-safety.js, NOTES-clone-safety.txt.

What is good
- Uses Engine / GW / GW_SETTINGS / GW_CONFIRM / GW_FEATURE_OFF family
  (aligned with ENGINE-MAP; not window.vm).
- Cached clone count + O(1) threads.length = 0 on Stop is the right idea
  for the reported Stop lag with huge thread lists.
- Default 300 cap; infinite clones requires explicit confirm.
- NOTES honestly list non-goals (frame budget, text/list caps, crash recovery)
  and that the module is not browser-tested.
- Feature-off key cloneSafety; idempotent GW_CLONE_SAFETY guard.

Risks
1. Reimplements g.createClone instead of wrapping the live implementation.
   NOTES already warn about dual historical createClone paths in app.html.
   Missing side effects (layering, speech, extension hooks) = silent bugs.
2. Capture-phase Stop/Green Flag listeners can race or double-clear with the
   real handlers; order must be verified in source.
3. Hat cache via #workspaceCanvas + data-type === 'when_clone' may not match
   G-Warp's actual hat DOM if structure differs.
4. effectiveLimit uses Math.min(BASE_LIMIT, project cloneLimit) when finite —
   good safety bias; document parity vs TurboWarp "infinite clones" projects.
5. Owner-reported 81k-clone / ~45s Stop remains REPORTED, not reproduced here.

Minimum correction / test gate (Claude + owner; not Grok)
- Diff optimizedCreateClone field-by-field against the effective live
  GW.createClone (v15.9-era path noted in NOTES).
- Prefer wrap-then-call original for unknown fields if parity is unclear.
- Controlled tests: 299/300/301 clones; nested clone hats; delete one/all;
  Stop latency measurement; infinite-clones confirm cancel/accept;
  double-load module; feature-off; Green Flag reset of warn flag.

Verdict: Keep as candidate for controlled testing. Do not call it a fix for
the unreproduced 81k case. MERGE-QUEUE PICK = "selected for test," not approved.
