PURPOSE
Give every AI a bounded role, ordered tasks, evidence requirements, acceptance criteria, and handoff gates. Prevent blind coding, duplicate research, guessed APIs, conflicting patches, repeated whole-app audits, and premature merging. ChatGPT is the standing independent cross-AI reviewer; every AI may review peers' work. See team/TODO-CHATGPT.txt, team/CROSS-AI-REVIEW-2026-10-15.txt and team/CONTINUOUS-WORK-QUEUE.txt. The owner decides priorities and approves anything shipped.

1. Creapter1 is product owner and final approver for priorities, design choices, live integration, and releases.
2. ALL AIs may inspect/use the existing app, research, reproduce and test assigned issues, write fixes, and prepare code proposals. Keep work in your own folder by default. No AI may edit another AI's folder or overwrite another contributor's work.
3. ALL AIs may place code in app.html/index.html only when explicitly assigned, and only as a uniquely marked, inert, non-executing proposal. Never connect it to live runtime, boot, event, import, rendering, UI, or serialization paths. If inert placement cannot be guaranteed, keep the complete candidate in the contributor's own folder and add no app-file code.
4. Claude Opus 5.5 is the ONLY AI authorized to connect/activate proposals, integrate them into live behavior, conduct the official side-by-side runtime/visual comparison, capture official screenshots/evidence, resolve competing candidates, and prepare releases. 5. No proposal is approved merely because it exists, passes syntax, or is labelled PICK. Owner approval is required before live integration/release.
6. This plan does not prove app.html/index.html are intact. The large app source was not fully verified in this planning pass.
7. Never claim a browser test, successful merge, backup, rollback, or fix unless it actually happened and evidence is recorded.
8. Preserve G-Warp; do not rebuild Scratch or make a replacement app. Do not remove existing features (“add, don't swap”). Follow STYLE-GUIDE, privacy, safety, and licensing requirements.
9. Never run arbitrary JavaScript blocks or silently transmit project/personal data. Sensitive extension behavior must be correctly marked and warned.
10. Before code work, read AI-TEAM.txt, TODO.txt, STYLE-GUIDE.txt, ENGINE-MAP.txt, MERGE-QUEUE.txt, this plan, and relevant notes. G-Warp is not scratch-vm. Verify real hooks and mark unknown APIs UNSURE rather than guessing.

12. Out-of-scope ideas must be preserved in team/FUTURE-IDEAS.txt as WAITING FOR OWNER; do not implement or integrate them without the owner's explicit approval.

STAGE 1B — REVIEW APPLICATIONS + ISOLATED CODING PROPOSALS (NEW OWNER RULE)
Purpose: let any AI that is already running/inspecting G-Warp contribute useful code without allowing that code to silently alter the working app. This applies to every AI, including Claude, ChatGPT, Grok, DeepSeek, Gemini, and any future AI.

PERMITTED FOR ALL AIs
- Open and use the current app to understand behavior, reproduce a specific bug, or collect observations, without claiming that a test passed unless it was actually run.
- Research, draft fixes, create code, compare approaches, and implement a proposal in the contributor's own folder.
- If the owner/task specifically calls for code to be placed inside app.html/index.html, add it ONLY in a uniquely named, clearly delimited, inert proposal block.
- Report exact changes, the reason, APIs/hooks assumed, expected behavior, risks, and tests performed/not performed.
- Suggest improvements to existing features and prepare optional ideas for later.

PROHIBITED FOR NON-INTEGRATION WORK
- Do not connect a proposal to the running app: no live function replacement, call sites, imports, script registration, boot hooks, active event listeners, CSS selectors that alter live UI, active feature flags, or serialization/initialization changes.
- Do not leave new code executing. Proposal blocks must be non-executable (for example, a clearly marked comment containing the candidate source or an inert text/template payload); do not paste raw executable statements into a live script.
- Do not rewrite, remove, rename, or reformat unrelated code; do not change current behavior as a side effect.
- Do not overwrite another AI's proposal or edit a shared file concurrently. Claim the file/task and record the base commit/blob ID first.
- Do not describe a dormant proposal as a completed fix.

REQUIRED PROPOSAL MARKERS
Use a unique ID and obvious boundaries, such as:
  GW-AI-PROPOSAL: <ID> | AUTHOR: <AI> | STATUS: DORMANT / NOT CONNECTED
  PURPOSE: <one sentence>
  TARGET: <file/module/feature>
  BASE COMMIT: <commit SHA>
  START: <unique proposal marker>
  [candidate code stored inertly; it must not execute]
  END: <unique proposal marker>
Do not nest or reuse IDs. If storing executable source inside comments is unsafe because of comment termination or HTML parsing, put the full candidate in the contributor's own folder and add only a short pointer in app.html.

ACCEPTANCE FOR EACH PROPOSAL
- Problem/goal and user impact
- Reproduction steps or explicit “new feature idea”
- Proposed code and exact location
- Evidence class: SOURCE-VERIFIED / STATIC-ANALYSIS / BROWSER-VERIFIED / NOT-TESTED
- Real API names used and source evidence
- Tests run and results, plus tests not run
- Performance/security/compatibility risks
- Expected visual change (if any)
- Status: DORMANT / READY FOR REVIEW / REJECTED / SELECTED / INTEGRATED / REGRESSION-TESTED
- No integration claim before the code is actually connected and tested
