0. HARD STOP GATES — BEFORE ENGINEERING
1. Verify the model label in the actual Claude interface is exactly “Claude Opus 5.5.” If absent, different, or ambiguous, do not integrate/activate code; tell the owner and stop at read-only review.
2. Get explicit owner approval for live integration/release. Being the designated integrator is not blanket approval.
3. Identify the known-good baseline: branch, commit SHA, app.html/index.html blob IDs, deployed URL and current deployed version. If uncertain or deployment diverges, ask the owner; do not guess.
4. Never rewrite app.html wholesale. Make the smallest localized patch; preserve unrelated features and original style. No broad redesign.
5. Never claim a test, backup, rollback, merge, or deployment succeeded unless it actually did and evidence is recorded.
6. Keep candidate work and notes in their owners' folders. Do not silently edit another AI's folder. Request a narrow revision from the original author or record your own integration patch separately with rationale.
7. The owner is final authority. If the owner has not approved integration, finish only read-only inventory, reproduction, and a proposed patch/test plan.

1. TOKEN-SAVING WORK LOOP
Use this loop for every issue:
A. Read only the current source area, the relevant notes, latest review, and diff. Do not reread the whole repository every time.
B. State the one bug/requirement, impact, and acceptance test in 3–6 lines.
C. Find the actual implementation and API names. Use ENGINE-MAP as an index, then verify current source. Mark unknowns UNSURE.
D. Choose one candidate/fix. Do not compare every A/B/C unless the current winner fails or evidence shows a material trade-off.
E. Create a minimal patch in a working copy/branch; preserve baseline commit and record changed files.
F. Run cheap checks first (syntax/lint/static checks), then the smallest targeted runtime test, then targeted regressions. Run full suite only when the change touches shared runtime, serialization, or broad UI behavior.
G. Report actual results in a compact table: test, expected, actual, PASS/FAIL/NOT RUN, evidence location.
H. If blocked, write the exact missing evidence/question and stop that branch of work; don't burn tokens speculating.
I. Append a resumable handoff and update the task/merge status after the work.

TOKEN BUDGET RULES
- No repeated broad research or full-app summaries when a current report exists. Read the latest report and changed dependencies only.
- No long chain-of-thought or speculative essay. Produce decisions, evidence, risks, and next action.
- Do not create more than one patch candidate per issue unless the first fails or a specific trade-off requires alternatives.
- Do not run all test cases after every tiny edit; use risk-based targeted regression, then a release-level suite at milestone.
- Do not inspect unrelated files. Use targeted search for symbols/selectors, then open only surrounding code.
- Stop and ask the owner when a product decision, canonical URL, model identity, baseline, privacy policy or irreversible action is unclear.
- Keep handoffs concise; link reports rather than copying them into every file.
- A test marked NOT RUN is preferable to an invented result.
